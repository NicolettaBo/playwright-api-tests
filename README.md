# Playwright API Tests

## Overview

This project uses Playwright Test and TypeScript to exercise selected endpoints of the public [JSONPlaceholder API](https://jsonplaceholder.typicode.com).

The tests focus on response status codes, JSON content types, response shapes, and representative field values. This is a deliberately limited selection of API coverage, not an exhaustive test of every JSONPlaceholder route.

### Assumptions

- The tests use JSONPlaceholder's publicly available fixture data and do not require credentials or a locally running service.
- JSONPlaceholder does not persist writes. POST, PUT, PATCH, and DELETE tests verify the immediate response only; they do not expect later requests to reflect changes.
- The tests assert selected characteristics of the fixture data, such as the collection of 100 posts and 100 albums.

### Scope completed

The current automated tests are in [`tests/`](./tests):

| Resource | Current coverage |
|---|---|
| Posts | GET collection and details (first, middle, and last); GET a nonexistent post; POST with a valid and nonexistent user ID; POST title edge cases (empty, whitespace-only, special characters, Unicode, and a line break); PUT, PATCH, and DELETE |
| Comments | GET collection; GET comments for an existing post and a nonexistent post |
| Albums | GET collection; GET albums for a user; GET albums for a nonexistent user |

Response checks include expected HTTP status codes, JSON content types for successful responses, response body shapes, selected field values, collection sizes or non-empty results, and empty results for selected nonexistent-resource filters.

## Execution Instructions

### Prerequisites

Install Node.js, which includes npm. Verify they are available from the project root:

```bash
node --version
npm --version
```

### Install dependencies

From the project root, install the dependencies listed in `package-lock.json`:

```bash
npm ci
```

This installs Playwright, TypeScript, and the Node.js type definitions used by the project. The project initialization commands (`npm init -y`, `npm init playwright@latest`, and `npm install --save-dev @types/node`) were used to set up the project and do not need to be rerun to execute it.

### Build

No separate build step is configured for this project.

### Run the tests

```bash
npm test
```

### Test prioritization

The title edge-case tests are lower-priority supplemental coverage and would normally be kept separate from high-priority tests so they can be selected independently. A larger suite could do this with Playwright tags or by placing them in a dedicated spec file. In this project, the edge cases are in a separate `test.describe` block, but `npm test` currently runs them together with the rest of the suite; separate tags, files, or npm scripts have not been configured.

### View test results

The Playwright HTML report is generated by the test run. Open it with:

```bash
npm run report
```

The configuration also prints a list-style test summary to the terminal.

## Coverage Summary

### Routes and resources tested

- Posts: `/posts`, `/posts/1`, `/posts/9999`, and POST, PUT, PATCH, and DELETE requests to `/posts` or `/posts/1`
- Comments: `/comments`, `/posts/1/comments`, and `/posts/9999/comments`
- Albums: `/albums`, `/users/1/albums`, and `/users/9999/albums`

#### Posts test-script route summary

The Posts spec makes **15 requests** across collection, detail, and write operations, including parameterized detail IDs and some POST title edge cases:

| Method | Endpoint | Purpose | Expected result |
|---|---|---|---|
| GET | `/posts/1` | Retrieve the first expected post | Valid post whose ID is `1` |
| GET | `/posts/50` | Retrieve a middle expected post | Valid post whose ID is `50` |
| GET | `/posts/100` | Retrieve the last expected post | Valid post whose ID is `100` |
| GET | `/posts` | Retrieve the posts collection | 100 valid posts with unique IDs |
| GET | `/posts/9999` | Retrieve a nonexistent post | HTTP `404` and an empty JSON object `{}` |
| POST | `/posts` | Create a post with an existing user ID | HTTP `201`; submitted fields are echoed and a positive ID is returned |
| POST | `/posts` | Create a post with a nonexistent user ID | HTTP `201`; submitted fields, including the nonexistent `userId`, are echoed and a positive ID is returned |
| POST | `/posts` | Submit empty, whitespace-only, special-character, Unicode, and line-break titles | HTTP `201`; each submitted title and other fields are echoed, and a positive ID is returned |
| PUT | `/posts/1` | Replace a post | Valid post containing the submitted replacement data |
| PATCH | `/posts/1` | Update a post's title | Valid post with the submitted title |
| DELETE | `/posts/1` | Delete a post | Successful response with an empty JSON object `{}` |

#### Comments test-script route summary

| Method | Endpoint | Purpose | Expected result |
|---|---|---|---|
| GET | `/comments` | Retrieve the comments collection | Non-empty array of valid comments with unique IDs and required fields |
| GET | `/posts/1/comments` | Retrieve comments associated with post `1` | Valid comments associated with post `1`, with no more than five results |
| GET | `/posts/9999/comments` | Retrieve comments for a nonexistent post | Empty array |

#### Albums test-script route summary

| Method | Endpoint | Purpose | Expected result |
|---|---|---|---|
| GET | `/albums` | Retrieve the albums collection | 100 valid albums with unique IDs and required fields |
| GET | `/users/1/albums` | Retrieve albums associated with user `1` | Non-empty array of valid albums, all associated with user `1` |
| GET | `/users/9999/albums` | Retrieve albums for a nonexistent user | Empty array |

### Types of validation

- HTTP status codes
- JSON response content type for successful responses
- Response object and array shapes using TypeScript type guards
- Key response fields, including IDs, associations, and non-empty text
- Collection expectations, including selected counts, non-empty collections, and unique IDs
- Empty arrays for selected nonexistent-user or nonexistent-parent filters
- Immediate response contents for POST, PUT, PATCH, and DELETE requests
- POST title edge cases: empty, whitespace-only, special-character, Unicode, and line-break inputs are accepted and echoed unchanged in the response

### Intentionally omitted

The assignment's remaining example resources—users, photos, and todos—do not currently have automated tests. Other routes and combinations are also outside this suite, including most resource detail and relationship routes, query-parameter variations, and write operations for comments and albums. The POST title cases provide edge-case input and response validation, but they do not establish input validation or rejection behavior. Other negative request scenarios and broader edge cases have not been covered. These omissions reflect the limited scope of the completed test work; they are documented here rather than represented as tested coverage.

Due to time constraints, other request variations such as very large input strings, missing or null fields, and invalid field types were not tested.

One not-found response is covered (`GET /posts/9999`, which returns HTTP `404` and an empty object). Other error responses and invalid-request scenarios are not covered. JSONPlaceholder may accept requests that a production API would reject, so additional negative tests would need clearly defined expected behavior.

Non-functional testing is outside the scope of this project.
